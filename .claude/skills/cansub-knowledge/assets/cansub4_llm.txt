# Introduction

The **CANsub.4** is a compact and professional CAN bus interface with four galvanically isolated CAN buses.
It combines high performance with features matching or exceeding those typically only found in larger, more expensive devices.

The device connects via either USB<sup>[1](#usb)</sup> or Ethernet, both exposing an identical network interface<sup>[2](#net)</sup>.

The device has an [LCD color display](hardware/display.md#display) providing useful information, such as CAN bus state, frame rate, and bus load.

A built-in web-based user interface (*webCAN*) can be accessed through a browser without installing any software<sup>[3](#tls)</sup>. The *webCAN* tool comes with a rich set of features, such as raw-frame view, decoded-frame view, and live plotting.

[Python-can](https://python-can.readthedocs.io/) support is provided through the [python-can-cansub](https://pypi.org/project/python-can-cansub/) package.

The CANsub.4 has an open [API](api/index.md#api) based on easily accessible technologies to encourage users to create 3rd-party integrations<sup>[4](#rd)</sup>.

![image](cansub4.jpg)

---
* <a id='usb'>**[1]**</a> Network over USB using the USB CDC-NCM device class.
* <a id='net'>**[2]**</a> Switching between USB and Ethernet requires only a URL change.
* <a id='tls'>**[3]**</a> A TLS certificate can optionally be installed in the browser.
* <a id='rd'>**[4]**</a> A range of 3rd party integrations and code examples are available on [csselectronics.com](https://csselectronics.com/).

## Usage

A typical integration follows this flow:

1. **Initialize**  *(once)*: Verify the API version and sync the device clock if needed (REST)
2. **Configure bus**  *(per bus)*: Configure CAN bus (REST)
3. **Open bus**: Connect WebSocket to open CAN bus (WebSocket)<sup>[2](#fn-websocket-client)</sup>
4. **Communicate**: Communicate with the CAN bus (WebSocket) and monitor states (REST)
5. **Close bus**: Disconnect WebSocket the close CAN bus (WebSocket)

For more details, see [REST API](api_rest.md#rest-api) and [WebSocket API](api_ws.md#websocket-api). See [Closing the connection](api_ws.md#closing-the-connection) for recommended close sequence.

---
* <a id='fn-websocket'>**[1]**</a> WebSocket is chosen over raw TCP socket to make the API web-friendly.
* <a id='fn-websocket-client'>**[2]**</a> Only a single client can be connected to the WebSocket of each bus.
* <a id='fn-python-can'>**[3]**</a> python-can support is provided through the [python-can-cansub](https://pypi.org/project/python-can-cansub/) package.

# Specification

## USB

* USB-C connector
* Powered through USB connector (5 V)
* USB CDC-NCM device class

## Ethernet

* RJ45 connector
* 10/100 base-t/tx IEEE 802.3 ethernet transceiver
* Link status LED

## Display

* 0.96” backlit LCD color display

## Network

* Network over USB (CDC-NCM) or Ethernet
* Discovery via mDNS
* Data secured using TLS
* Optional user authentication using TLS Mutual Authentication (mTLS)

## CAN bus

* Physical
  > * Four galvanically isolated<sup>[1](#fn-basic-isolation)</sup> physical CAN bus interfaces
  > * DB25 (D-sub25) connector
* Transceiver
  > * Compliant with ISO 11898-2:2016 (classical CAN and CAN-FD)
  > * Short-circuit, bus-fault, and undervoltage protection
  > * Ideal passive behavior when unpowered (high impedance / no load)
  > * TXD dominant timeout (prevents network blocking in the event of a failure)
* Controller
  > * Based on MCAN IP from Bosch
  > * Customizable bit-rate / bit-timing / sample-point
  > * Customizable hardware filters (range or mask)
  > * Support for bus-error monitoring
  > * Support for listen-only mode (transmission disabled)
  > * High resolution frame timestamping (1 us) on both RX and TX
* Application
  > * Frame-rate, frame-count, and bus-load calculated by device
  > * Hardware transmission jobs for high accuracy frame spacing
  > * Frame transmission acknowledgements with actual transmission timestamps

## Mechanical

* Robust aluminum enclosure
* Flanges for secure mounting
* Dimensions: 67 x 87 x 20 mm (L x W x H)
* Operating temperature: -25 °C to +70 °C

---
* <a id='fn-basic-isolation'>**[1]**</a> The CANsub.4 implements a *basic* galvanic isolation, making it easy to connect CAN bus networks not subjected to high voltage differences.

# Security

Data transferred over the device network interface (USB or Ethernet) is secured by Transport Layer Security (TLS). TLS ensures that data exchanged with the CANsub.4 is encrypted and it ensures that the user is connecting to a genuine CANsub device. When connected via Ethernet, access can optionally be restricted using [TLS Mutual Authentication](mtls.md#tls-mutual-authentication-mtls).

#### NOTE
In TLS terminology, a *user* uses a *client* application, such as a browser, to establish a secure connection to a *server* (CANsub.4).

The CANsub.4 proves it is genuine using a built-in certificate, signed by the root certificate below.

[`CANsub root certificate`](/../assets_collected/cansub4/cansub_root_cert.crt)
<br/>
`SHA-256 fingerprint = D064C85905195400216A11BB50D754865ED2B5F997D36A9EA2EA97883B15D0F1`
<br/>

#### NOTE
A client can be made to trust the CANsub.4 by installing the CANsub root certificate. For more information on how to install the root certificate, see [CANsub certificate installation](../../getting_started/certificate/index.md#cansub-certificate-installation).

The table below provides an overview of the CANsub-root (shared) and CANsub-device (device specific) certificate parameters.

| Parameter           | Root certificate   | Device certificate                                       |
|---------------------|--------------------|----------------------------------------------------------|
| Key algorithm       | ECDSA P-256        | ECDSA P-256                                              |
| Signature algorithm | ECDSA-SHA256       | ECDSA-SHA256                                             |
| Issued to           | `CANsub root`      | `CANsub [DEVICE-ID]`                                     |
| Hostnames (SAN)     |                    | `[DEVICE-ID]-usb.local`<br/><br/>`[DEVICE-ID]-eth.local` |

#### NOTE
The device certificate Subject Alternative Name (SAN) field allows for hostname verification. Hostname verification is **not** possible when the device is accessed via an IP address.

The CANsub.4 always uses the TLS cipher suite: `ECDHE-ECDSA-AES128-GCM-SHA256`<sup>[1](#fn-cipher-suite)</sup>.

Certificate validity periods (`notBefore` and `notAfter`) are not enforced because the CANsub.4 does not know the time at power-on.

A simplified illustration of the TLS handshake is provided in the [TLS handshake](tls_handshake.md#tls-handshake) diagram.

---
* <a id='fn-cipher-suite'>**[1]**</a> The client must support the cipher suite for the TLS handshake to succeed.

## Device time

Provides access to the device time (wall-time). The device time needs to be set for the device to be able to correctly timestamp CAN bus frames.

#### NOTE
The time is reset on power-cycles and is shared across all CAN channels.

### GET /api/time

**Get device time**

Returns the current device time as an RFC3339/ISO-8601 UTC timestamp string (JSON string).

**Example request:**

```http
GET /api/time HTTP/1.1
Host: example.com
```

* **Status Codes:**
  * [200 OK](https://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html#sec10.2.1) – 

    Current device time.

    **Example response:**
    ```http
    HTTP/1.1 200 OK
    Content-Type: application/json

    2025-01-01T00:00:00.000Z
    ```

### PUT /api/time

**Set device time**

Sets the device time using an RFC3339/ISO-8601 UTC timestamp string (JSON string).

**Example request:**


## Client certificate

Manages the client certificate used as the trust anchor for [TLS Mutual Authentication (mTLS)](../connection/security/mtls.md#tls-mutual-authentication-mtls). Upload (PUT) a certificate to enable mTLS, read (GET) the SHA-256 fingerprint of the loaded certificate, or remove (DELETE) the certificate to disable mTLS.

### GET /api/client-cert

**Get client certificate identifier**

Returns the SHA-256 fingerprint of the DER-encoded client certificate currently loaded as the trust anchor for TLS mutual authentication.

**Example request:**

```http
GET /api/client-cert HTTP/1.1
Host: example.com
```

* **Status Codes:**
  * [200 OK](https://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html#sec10.2.1) – 

    SHA-256 fingerprint of the loaded client certificate as a 64-digit hexadecimal value.

    **Example response:**
    ```http
    HTTP/1.1 200 OK
    Content-Type: application/json

    00112233445566778899aabbccddeeff00112233445566778899aabbccddeeff
    ```
  * [404 Not Found](https://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html#sec10.4.5) – No client certificate loaded (mutual authentication disabled).

### PUT /api/client-cert

**Upload client certificate**

Uploads the client public certificate (PEM format) used as the trust anchor for TLS mutual authentication, replacing any existing certificate.

**Example request:**

```http
PUT /api/client-cert HTTP/1.1
Host: example.com
Content-Type: application/x-pem-file

-----BEGIN CERTIFICATE-----
...
-----END CERTIFICATE-----
```

* **Status Codes:**
  * [200 OK](https://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html#sec10.2.1) – Certificate stored. Mutual authentication enabled.
  * [400 Bad Request](https://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html#sec10.4.1) – Bad request (not a valid X.509 certificate).
  * [413 Request Entity Too Large](https://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html#sec10.4.14) – Payload too large.

### DELETE /api/client-cert

**Remove client certificate**

Removes the stored client certificate, disabling TLS mutual authentication.

* **Status Codes:**
  * [200 OK](https://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html#sec10.2.1) – Certificate removed. Mutual authentication disabled.
  * [404 Not Found](https://www.w3.org/Protocols/rfc2616/rfc2616-sec10.html#sec10.4.5) – No client certificate loaded.

The GET response (SHA-256 fingerprint) has the following format.

| type      | *string*       |
|-----------|----------------|
| maxLength | 64             |
| minLength | 64             |
| pattern   | ^[0-9a-f]{64}$ |

## CAN {channel} transmit

Transmit-sequences are transmission *jobs* submitted to the device, allowing for hardware-controlled high precision transmissions (even on high-latency networks). A transmit-sequence contains a list of CAN frames to transmit and a set of parameters to control the transmission (see the parameter descriptions below).

List (GET) and create (POST) transmit-sequences of a specific CAN channel. A new transmission sequence is created with `count` set to `limit` - update the `count` value (e.g. to zero) to start the transmission-sequence. When a transmission sequence is created, the ID is returned via the *Location* header field.

# WebSocket API

The WebSocket API is used for transfer of CAN bus frames between the connected client and the CANsub.4.

This page uses the term *frame* in three distinct contexts:

- **CAN frame**: A CAN-bus frame.
- **HDLC frame**: A delimited binary container for boundary detection and integrity verification.
- **Network frame**: A network-layer data frame.

#### NOTE
Device configuration and state monitoring are done via the [REST API](api_rest.md#rest-api).

---

## WebSocket usage

The `/api/can/{channel}/ws` endpoints (one for each physical channel) accept WebSocket upgrades. A single client can be connected to each WebSocket. Live data is transferred using WebSocket **binary messages**. The format of the binary data is described below.

**Connecting a WebSocket opens the associated CAN bus (channel) on the device. Disconnecting closes the channel** (see [Closing the connection](#closing-the-connection)).

The connection is bidirectional:

- **CANsub → Client**: the CANsub sends received CAN frames, CAN transmission acknowledgements, and CAN error frames.
- **Client → CANsub**: the client sends CAN frames to be transmitted on a physical CAN bus.

### Receive

Receiving data from the WebSocket is illustrated (simplified) below. Reception follows the steps (explained in more details below):

1. Read bytes from WebSocket until a start and end boundary byte is found.
2. Perform byte de-stuffing and remove boundary bytes.
3. Validate CRC32.
4. Perform CAN frame deserialization until no more bytes (can contain one or more CAN frames).

### Transmit

Transmitting data to the WebSocket is illustrated (simplified) below. Transmission follows the steps (explained in more details below):

1. Serialize CAN frames (one or more).
2. Calculate CRC32.
3. Perform byte stuffing and add boundary bytes.
4. Write bytes to WebSocket<sup>[1](#fn-websocket-max)</sup>.

---

## Closing the connection

A WebSocket connection is closed by sending a WebSocket close message to the CANsub.4. When the CANsub.4 receives the WebSocket close message, it performs the following steps:

1. Completes queued CAN frame transmissions (without timeout)
2. Closes the CAN bus
3. Confirms the WebSocket close message

The client can abort step 1 by performing a [DELETE request](api_rest.md#can-channel-websocket) to the WebSocket endpoint `/api/can/{channel}/ws`. The CANsub.4 then discards the queued CAN frames and completes the close immediately. The `DELETE` request can be used as a client controlled timeout for step 1.

### Recommended close sequence

1. Send a WebSocket close message.
2. Await close confirmation.
3. If no confirmation arrives within a (client controlled) timeout period, issue a `DELETE` request and await the confirmation which should now arrive immediately.

#### NOTE
Use the WebSocket close handshake when closing the connection. Avoid closing the TCP connection directly.

## HDLC frame

Each HDLC frame carries one or more serialized CAN frames. HDLC framing provides boundary detection, payload integrity verification, and byte-stuffing.

#### HDLC frame structure

| Boundary byte   | Payload           | CRC32   | Boundary byte   |
|-----------------|-------------------|---------|-----------------|
| `0x7E`          | N bytes (stuffed) | 4 B     | `0x7E`          |
- `0x7E` marks the start and end of each HDLC frame.
- *payload*: one or more serialized CAN frames concatenated (see [CAN frame]()).
- *CRC32*: IEEE 802.3 CRC32 (polynomial `0xEDB88320`) computed over the raw (un-stuffed) payload bytes, appended big-endian.
- Byte-stuffing is applied to all bytes between the boundary bytes (payload + CRC32 bytes).

### Byte-stuffing

Byte-stuffing ensures that boundary byte (`0x7E`) does not appear in the HDLC frame body. Before transmission, every payload and CRC32 byte is stuffed.

#### Byte-stuffing substitutions

| Original   | Encoded sequence   |
|------------|--------------------|
| `0x7E`     | `0x7D` `0x5E`      |
| `0x7D`     | `0x7D` `0x5D`      |

The escape byte `0x7D` is always followed by the original byte XOR `0x20`. On decoding, each `0x7D` causes the next byte to be XOR-ed with `0x20` to recover the original value.

## CAN frame

CAN bus frames are serialized as specified below.

#### `CB`: Classical-Base, `CE`: Classical-Extended, `FB`: FD-Base, `FE`: FD-Extended, `ER`: Error

|     |           |        |     |     |     |     |        |    |    |    |    |    |    |   Byte |   0-5 |   6 |   7 | 8   | 9   | 10   |
|-----|-----------|--------|-----|-----|-----|-----|--------|----|----|----|----|----|----|--------|-------|-----|-----|-----|-----|------|
| Bit | 47-0      | 7      | 6   | 5   | 4   | 3   | 2      |  1 |  0 | 7  |  6 | 5  | 4  |      3 |     2 |   1 |   0 | 7-0 | 7-0 | 7-0  |
| CB  | TIMESTAMP | FDF(0) | RTR | 0   | TX  | DLC | IDE(0) |  0 |  0 | 0  |  0 | ID | -  |        |       |     |     |     |     |      |
| CE  | TIMESTAMP | FDF(0) | RTR | 0   | TX  | DLC | IDE(1) |  0 |  0 | ID |    |    |    |        |       |     |     |     |     |      |
| FB  | TIMESTAMP | FDF(1) | BRS | ESI | TX  | DLC | IDE(0) |  0 |  0 | 0  |  0 | ID | -  |        |       |     |     |     |     |      |
| FE  | TIMESTAMP | FDF(1) | BRS | ESI | TX  | DLC | IDE(1) |  0 |  0 | ID |    |    |    |        |       |     |     |     |     |      |
| ER  | TIMESTAMP | 0      | 0   | 1   | ERR | -   |        |    |    |    |    |    |    |        |       |     |     |     |     |      |
- `TIMESTAMP`: Timestamp in microseconds since 2025/01/01 00:00:00 UTC (offset: 1735689600000000 µs)
- `FDF`: FD Format Indicator
- `RTR`: Remote Transmission Request
- `BRS`: Bit Rate Switch
- `ESI`: Error State Indicator
- `TX`: Transmission Acknowledgement
- `DLC`: DLC
- `IDE`: Identifier Extension
- `ID`:  Identifier
- `ERR`: Error Frame
  > - `0`: Bit (bit0/bit1)
  > - `1`: Ack
  > - `2`: Form
  > - `3`: Stuff
  > - `4`: Crc

# Install client certificate (mTLS)

When mTLS is enabled, the CANsub.4 only grants access to a browser that presents a valid client certificate and key. The [Enable Mutual Authentication](../mtls.md#enable-mutual-authentication) guide bundle the client certificate and key into a single PKCS#12 file (`[CLIENT-NAME].p12`) for this purpose.

This page covers importing that bundle into Chrome and Firefox. OS-level installation is outside the scope of this manual.

> ##### Client certificate installation guides
> 
> * [Chrome browser](#chrome-browser)
> * [Firefox browser](#firefox-browser)

#### NOTE
Steps may differ slightly depending on OS and browser version.

---

## Chrome browser

1. Enter the following URL in the Chrome address bar to open the Certificate Manager.
   ```text
   chrome://certificate-manager/
   ```

   ![image](getting_started/certificate/chrome_1.png)
2. Click *Your certificates* and *Manage imported certificates from …* or *View imported certificates from …* (depends on OS and version).
   ![image](connection/security/client_certificate/chrome_2.png)
3. Click *Import*.
   ![image](connection/security/client_certificate/chrome_3.png)
4. Navigate to the client certificate bundle file (`.p12`) and click *Select*. Ensure the file extension filter includes `.p12`.
   ![image](connection/security/client_certificate/chrome_4.png)
5. Enter the *certificate password* chosen when the `.p12` was created (if any, else leave blank).
   ![image](connection/security/client_certificate/chrome_5.png)
6. The certificate is now listed under *Your certificates*.
   ![image](connection/security/client_certificate/chrome_6.png)
7. When accessing the CANsub.4 over the Ethernet connection, the browser will now prompt you to select a client certificate to use. Select the installed certificate and press *OK*.
   ![image](connection/security/client_certificate/chrome_7.png)

# Data interface

The device selects which data interface to use based on the following logic<sup>[1](#fn-change-mode)</sup>:

The detection state is shown on the device display, see [Connection layout](../hardware/display.md#connection-layout).

#### NOTE
The device uses distinct hostnames for the USB (`[DEVICE-ID]-usb.local`) and Ethernet (`[DEVICE-ID]-eth.local`) interfaces to prevent hostname resolution conflicts when switching between the two.

---

## USB-mode

In *USB-mode* the device is powered via USB and transfers data via USB.

When transferring data over USB, the device uses the USB CDC-NCM class<sup>[3](#fn-cdc-ncm)</sup> to expose a network interface. When using this mode, the device starts a DHCP server, ready to assign an IP address to the connected USB host.

| Hostname          | DHCP   | Network       | Device IPv4   | Host IPv4    |
|-------------------|--------|---------------|---------------|--------------|
| `[DEVICE-ID]-usb` | Server | `10.x.y.0/24` | `10.x.y.1`    | `10.x.y.100` |

The device hostname and IP are shown on the device display, see [Network layout](../hardware/display.md#network-layout).

The webpage hosted by the device can be accessed via:

- `https://[DEVICE-ID]-usb.local`<sup>[2](#fn-local)</sup> (e.g. `https://aabbccdd-usb.local`)
- `https://[DEVICE-IP]` (e.g. `https://10.119.41.1`)

The CANsub.4 is identified on the USB bus by the following vendor and product IDs:

| Parameter        | Value    |
|------------------|----------|
| Vendor ID (VID)  | `0x04D8` |
| Product ID (PID) | `0xE487` |

The device variant, hardware version, firmware version, and ID are stored in the USB descriptors.

```console
$ lsusb -v -d 04d8:e487 | grep -e "iProduct" -e "iSerial"
  iProduct                2 CANsub.4 01.02 01.02.03
  iSerial                 3 aabbccdd
```

---

## Ethernet-mode

In *Ethernet-mode* the device is powered via USB (charger) and transfers data via Ethernet.

#### NOTE
An optional Power-over-Ethernet (PoE) adapter is available.

| Hostname          | DHCP   | Device IPv4   |
|-------------------|--------|---------------|
| `[DEVICE-ID]-eth` | Client | Assigned      |

The device hostname and IP are shown on the device display, see [Network layout](../hardware/display.md#network-layout).

#### NOTE
The device obtains its IP address from a DHCP server (required). The device MAC address can be found via the [label](../hardware/label.md#label) or [display](../hardware/display.md#information-layout).

The webpage hosted by the device can be accessed via:

- `https://[DEVICE-ID]-eth.local`<sup>[2](#fn-local)</sup> (e.g. `https://aabbccdd-eth.local`)
- `https://[DEVICE-IP]` (e.g. `https://192.168.1.100`)

# detection.html.md

# Detection

#### NOTE
The device ID is printed on the device enclosure and can be used to construct the device hostname as explained in [Data interface](data_interface.md#data-interface) and [Getting started](../getting_started/index.md#getting-started). This section explains how to detect a CANsub device when the device ID is unknown.

The CANsub.4 advertises itself on the local network (USB or Ethernet) using mDNS<sup>[1](#fn-mdns)</sup> and DNS-SD<sup>[2](#fn-dnssd)</sup>. This allows the device to be discovered without knowing its IP address in advance.

The device registers a service of type `_cansub._tcp` with the following properties:

| Property        | Value                                                                       |
|-----------------|-----------------------------------------------------------------------------|
| Service type    | `_cansub._tcp`                                                              |
| Hostname        | `[HOSTNAME].local`<br/>(`[DEVICE-ID]-usb.local` or `[DEVICE-ID]-eth.local`) |
| Port            | `443`                                                                       |
| TXT: `api`      | REST API version (e.g. `02.00`)                                             |
| TXT: `channels` | Number of CAN-bus channels (`1`, `2`, or `4`)                               |

### Windows

On Windows, the `dns-sd`<sup>[3](#fn-dnssd-win)</sup> tool can be used for mDNS discovery.

```doscon
C:\>dns-sd -Z _cansub._tcp local

_cansub._tcp                                    PTR     aabbccdd-usb._cansub._tcp
aabbccdd-usb._cansub._tcp                       TXT     "api=02.00" "channels=4"
```

### Linux

On Linux, the `avahi-browse`<sup>[4](#fn-avahi)</sup> tool can be used for mDNS discovery.

```console
$ avahi-browse _cansub._tcp --resolve

= enx00005e005301 IPv4 aabbccdd-usb     _cansub._tcp         local
hostname = [aabbccdd-usb.local]
address = [10.201.129.1]
port = [443]
txt = ["channels=4" "api=02.00"]
```

---
* <a id='fn-mdns'>**[1]**</a> mDNS (Multicast DNS, RFC 6762) resolves hostnames on a local network without a DNS server.
* <a id='fn-dnssd'>**[2]**</a> DNS-SD (DNS Service Discovery, RFC 6763) advertises services on a local network.
* <a id='fn-dnssd-win'>**[3]**</a> `dns-sd.exe` is included with [Bonjour for Windows](https://support.apple.com/kb/DL999) (Apple).
* <a id='fn-avahi'>**[4]**</a> `avahi-browse` is part of the `avahi-utils` package.

# mtls.html.md

# TLS Mutual Authentication (mTLS)

By default, TLS encrypts the connection but does not determine *who* is allowed to connect to the CANsub.4. TLS Mutual Authentication (mTLS) adds client verification, ensuring that only authenticated users can access the device, similar to password protection.

TLS Mutual Authentication uses asymmetric cryptography, enabling it does not require storing any client secrets on the device. Only public certificate material is needed.

The CANsub.4 optionally supports mTLS **over the Ethernet connection**<sup>[1](#fn-mtls-persistent)</sup>.

#### NOTE
The USB connection can always be used to regain access to the device (mTLS is never enforced over USB), for example if the client certificate or key is lost.

---

## Enable Mutual Authentication

The steps below require the command-line tools **bash**, **OpenSSL**<sup>[2](#fn-openssl)</sup>, and **curl**. These are available by default on Linux and macOS. On Windows, all are provided through [Git Bash](https://git-scm.com/download/win) (a terminal including commonly used command-line tools). Once installed, the Git Bash tool can be opened through the start menu.

1. [Create a client certificate](#create-a-client-certificate).
2. [Upload the client certificate](#upload-the-client-certificate)
3. [Install the client certificate](#install-the-client-certificate)

The screen recording below demonstrates how to use Git Bash on Windows to perform steps 1 and 2. The CANsub root certificate (`cansub_root_cert.crt`) and the client certificate script (`demo_cansub_self_signed_cert.sh`) have been placed in directory `C:\Users\css\Desktop\mtls\`.

<hr class="docutils" style="clear:both;">

### 1. Create a client certificate

This step demonstrates how to create a **self-signed** client certificate suitable for a single user of a single device. For multiple users or multiple devices, consider a [CA-signed certificate](#ca-signed-certificate) (advanced).

The script<sup>[3](#fn-script-is-doc)</sup> below uses OpenSSL to create a client certificate. The public certificate is uploaded directly to the CANsub.4, which then trusts only that one certificate.

Download, inspect, and run the script with a client name (user name) and an optional password (used to protect the `.p12` bundle):

[`demo_cansub_self_signed_cert.sh`](client_certificate/demo_cansub_self_signed_cert.sh)
<br/>
```console
$ bash demo_cansub_self_signed_cert.sh [CLIENT-NAME] [PASSWORD]
```

The script generates the following files:

| File                | Sensitive   | Purpose                                                        |
|---------------------|-------------|----------------------------------------------------------------|
| `[CLIENT-NAME].crt` | No          | Client public certificate. Uploaded to the CANsub.4.           |
| `[CLIENT-NAME].key` | Yes         | Client private key.                                            |
| `[CLIENT-NAME].p12` | Yes         | Client `crt` and `key` bundled in one file for browser import. |
<details>
<summary>Show demo_cansub_self_signed_cert.sh</summary>
```bash
#!/bin/bash
set -euo pipefail

# Minimum steps to create a self-signed client certificate + key for mTLS.
# Usage: ./demo_cansub_self_signed_cert.sh [client_name] [password]

# Disable Git Bash (MSYS) path conversion on Windows (no effect on Linux/macOS).
export MSYS_NO_PATHCONV=1

CLIENT_NAME=${1:-client}
CLIENT_PASSWORD=${2:-}

CLIENT_KEY="${CLIENT_NAME}.key"
CLIENT_CRT="${CLIENT_NAME}.crt"
CLIENT_P12="${CLIENT_NAME}.p12"

# 1. Generate a private key (EC P-256, supported by the CANsub)
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:prime256v1 -out "${CLIENT_KEY}"
chmod 600 "${CLIENT_KEY}"

# 2. Generate a self-signed client certificate.
#    The extensions below make it a valid TLS client certificate:
#      basicConstraints=CA:FALSE     end-entity certificate, not a CA
#      keyUsage=digitalSignature     lets the client sign during the TLS handshake
#      extendedKeyUsage=clientAuth   marks the certificate for client authentication
openssl req -x509 -new -sha256 -key "${CLIENT_KEY}" -out "${CLIENT_CRT}" -days 3650 \
    -subj "/CN=${CLIENT_NAME}" \
    -addext "basicConstraints=critical,CA:FALSE" \
    -addext "keyUsage=critical,digitalSignature" \
    -addext "extendedKeyUsage=clientAuth"

# 3. Create a PKCS#12 bundle for browsers.
openssl pkcs12 -export -out "${CLIENT_P12}" \
    -inkey "${CLIENT_KEY}" \
    -in "${CLIENT_CRT}" \
    -name "${CLIENT_NAME}" \
    -passout "pass:${CLIENT_PASSWORD}"

if [ -z "${CLIENT_PASSWORD}" ]; then
    echo "Generated: ${CLIENT_KEY}, ${CLIENT_CRT}, ${CLIENT_P12} (no password)"
else
    echo "Generated: ${CLIENT_KEY}, ${CLIENT_CRT}, ${CLIENT_P12} (with password)"
fi
```

</details>

---

### 2. Upload the client certificate

This step demonstrates how to upload the client certificate to the CANsub.4 using the command-line tool curl<sup>[4](#fn-revoke)</sup> with the CANsub.4 connected via USB (`-usb.local`).

Download the CANsub root certificate, required to connect to the CANsub.4.

[`cansub_root_cert.crt`](/../assets_collected/cansub4/cansub_root_cert.crt)
<br/>

Replace `[CERTIFICATE-NAME]` with the name of the certificate to upload (e.g. `client`). Replace `[DEVICE-ID]` with the CANsub.4 device ID (e.g. `aabbccdd`).

```console
$ curl --cacert cansub_root_cert.crt --ssl-no-revoke -i -X PUT --data-binary @[CERTIFICATE-NAME].crt https://[DEVICE-ID]-usb.local/api/client-cert

HTTP/1.1 200
```

If the command returns `HTTP/1.1 200`, the certificate is accepted and Mutual Authentication is enabled.

The *fingerprint* of the loaded certificate can optionally be [verified](#verify-the-loaded-certificate).
Mutual Authentication can be disabled again by [removing](#remove-the-certificate) the certificate.

---

### 3. Install the client certificate

With Mutual Authentication enabled, clients connecting to the device must present the client certificate and key to gain access over the Ethernet connection. How to install the client certificate depends on the tool used to connect to the CANsub.4.

For a browser, see [Install client certificate (mTLS)](client_certificate/client_cert_install.md#install-client-certificate-mtls).

Mutual Authentication can optionally be [tested using curl](#test-mutual-authentication) (advanced).

### CA-signed certificate

A certificate authority (CA) signs client certificates. Uploading the CA certificate (`ca.crt`) to the CANsub.4 makes it trust every client certificate the CA signs. New clients can then be added without changing the CANsub.4, and the same CA certificate can be uploaded to multiple CANsub devices.

#### NOTE
When using a CA-signed certificate, ensure to upload `ca.crt` in [step 2](#upload-the-client-certificate) (rather than an individual client certificate). The CANsub.4 then trusts every client the CA signs.

The script<sup>[3](#fn-script-is-doc)</sup> below uses OpenSSL to create the CA and sign client certificates. Download, inspect, and run it once per client. The CA is created on the first run and reused for every client added afterwards:

[`demo_cansub_ca_signed_cert.sh`](client_certificate/demo_cansub_ca_signed_cert.sh)
<br/>
```console
$ bash demo_cansub_ca_signed_cert.sh [CLIENT-NAME] [PASSWORD]
```

```console
$ bash demo_cansub_ca_signed_cert.sh [CLIENT-NAME] [PASSWORD]
```

The script generates the following files:

| File                | Sensitive   | Purpose                                                        |
|---------------------|-------------|----------------------------------------------------------------|
| `ca.crt`            | No          | CA public certificate. Uploaded to the CANsub.4.               |
| `ca.key`            | Yes         | CA private key. Signs client certificates.                     |
| `[CLIENT-NAME].crt` | No          | Client public certificate. Signed by the CA.                   |
| `[CLIENT-NAME].key` | Yes         | Client private key.                                            |
| `[CLIENT-NAME].p12` | Yes         | Client `crt` and `key` bundled in one file for browser import. |
<details>
<summary>Show demo_cansub_ca_signed_cert.sh</summary>
```bash
#!/bin/bash
set -euo pipefail

# Minimum steps to create a CA-signed client certificate + key for mTLS.
# Usage: ./demo_cansub_ca_signed_cert.sh [client_name] [password]
# Re-run with a different client_name to enroll more users (the CA is reused).

# Disable Git Bash (MSYS) path conversion on Windows (no effect on Linux/macOS).
export MSYS_NO_PATHCONV=1

CLIENT_NAME=${1:-client}
CLIENT_PASSWORD=${2:-}

CLIENT_KEY="${CLIENT_NAME}.key"
CLIENT_CRT="${CLIENT_NAME}.crt"
CLIENT_P12="${CLIENT_NAME}.p12"
CLIENT_CSR="${CLIENT_NAME}.csr"

CA_NAME="CANsub Client CA"
CA_KEY="ca.key"
CA_CRT="ca.crt"
CA_CREATED=false

if [ ! -f "${CA_KEY}" ]; then

    # 1. Generate the root CA private key (EC P-256, supported by the CANsub).
    #    The CA key is reused to sign future client certificates.
    openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:prime256v1 -out "${CA_KEY}"
    chmod 600 "${CA_KEY}"

    # 2. Generate the self-signed root CA certificate.
    #    basicConstraints=CA:TRUE and keyUsage=keyCertSign let it sign client certificates.
    openssl req -x509 -new -sha256 -key "${CA_KEY}" -out "${CA_CRT}" -days 7300 \
        -subj "/CN=${CA_NAME}" \
        -addext "basicConstraints=critical,CA:TRUE" \
        -addext "keyUsage=critical,keyCertSign"

    CA_CREATED=true
fi

# 3. Generate a private key (EC P-256, supported by the CANsub)
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:prime256v1 -out "${CLIENT_KEY}"
chmod 600 "${CLIENT_KEY}"

# 4. Generate a certificate signing request (CSR) for the client.
#    The requested extensions make it a valid TLS client certificate:
#      basicConstraints=CA:FALSE     end-entity certificate, not a CA
#      keyUsage=digitalSignature     lets the client sign during the TLS handshake
#      extendedKeyUsage=clientAuth   marks the certificate for client authentication
openssl req -new -sha256 -key "${CLIENT_KEY}" -out "${CLIENT_CSR}" \
    -subj "/CN=${CLIENT_NAME}" \
    -addext "basicConstraints=critical,CA:FALSE" \
    -addext "keyUsage=critical,digitalSignature" \
    -addext "extendedKeyUsage=clientAuth"

# 5. Sign the CSR with the CA, copying the requested extensions into the certificate.
openssl x509 -req -sha256 -in "${CLIENT_CSR}" -out "${CLIENT_CRT}" -days 3650 \
    -CA "${CA_CRT}" -CAkey "${CA_KEY}" \
    -copy_extensions copy

# Remove the intermediate CSR.
rm -f "${CLIENT_CSR}"

# 6. Create a PKCS#12 bundle for browsers.
openssl pkcs12 -export -out "${CLIENT_P12}" \
    -inkey "${CLIENT_KEY}" \
    -in "${CLIENT_CRT}" \
    -name "${CLIENT_NAME}" \
    -passout "pass:${CLIENT_PASSWORD}"

# Report the generated files, distinguishing a newly created CA from a reused one.
if [ "${CA_CREATED}" = true ]; then
    echo "Created CA: ${CA_CRT}, ${CA_KEY}"
else
    echo "Reused existing CA: ${CA_CRT}, ${CA_KEY}"
fi

if [ -z "${CLIENT_PASSWORD}" ]; then
    echo "Generated client files: ${CLIENT_KEY}, ${CLIENT_CRT}, ${CLIENT_P12} (no password)"
else
    echo "Generated client files: ${CLIENT_KEY}, ${CLIENT_CRT}, ${CLIENT_P12} (with password)"
fi
```

### Verify the loaded certificate

A client certificate can be verified using curl<sup>[4](#fn-revoke)</sup>. The CANsub.4 returns `HTTP/1.1 200` and the SHA-256 fingerprint<sup>[5](#fn-sha256-der)</sup> if a certificate is currently loaded.

Replace `[DEVICE-ID]` with the CANsub.4 device ID.

```console
$ curl --cacert cansub_root_cert.crt --ssl-no-revoke -i -X GET https://[DEVICE-ID]-usb.local/api/client-cert

HTTP/1.1 200
"fdd181cfe35cfc7a04e2e0554c5c48bd7b10593d3e41c545418756f1316cc2bd"
```

A directly comparable fingerprint of a certificate stored as a file can be calculated using OpenSSL.

Replace `[CERTIFICATE-NAME]` with the base name of the certificate (e.g. `client` or `ca`).

```console
$ openssl x509 -in [CERTIFICATE-NAME].crt -outform DER | openssl dgst -sha256
SHA2-256(stdin)= fdd181cfe35cfc7a04e2e0554c5c48bd7b10593d3e41c545418756f1316cc2bd
```

### Remove the certificate

A client certificate can be removed and mTLS disabled using curl<sup>[4](#fn-revoke)</sup>. The CANsub.4 returns `HTTP/1.1 200` if the certificate is successfully removed.

Replace `[DEVICE-ID]` with the CANsub.4 device ID.

```console
$ curl --cacert cansub_root_cert.crt --ssl-no-revoke -i -X DELETE https://[DEVICE-ID]-usb.local/api/client-cert

HTTP/1.1 200
```

### Test Mutual Authentication

#### NOTE
The test below does not work on Windows (even with Git Bash): curl cannot load a client certificate from a file.

Mutual Authentication can be tested using curl<sup>[4](#fn-revoke)</sup> with the CANsub.4 **connected via Ethernet** (`-eth.local`).

Replace `[DEVICE-ID]` with the CANsub.4 device ID.

```console
$ curl --cacert cansub_root_cert.crt --ssl-no-revoke -i -X GET \
    https://[DEVICE-ID]-eth.local/api/version

curl: (35) OpenSSL SSL_connect: SSL_ERROR_SYSCALL in connection to [DEVICE-ID]-eth.local:443
```

The `--cert` argument provides the client certificate as the PKCS#12 bundle (`[CLIENT-NAME].p12`). Replace `[PASSWORD]` with the password entered when the bundle was created.

```console
$ curl --cacert cansub_root_cert.crt --ssl-no-revoke -i -X GET \
    --cert [CLIENT-NAME].p12:[PASSWORD] --cert-type P12 \
    https://[DEVICE-ID]-eth.local/api/version

HTTP/1.1 200
"12.34"
```

* <a id='fn-openssl'>**[2]**</a> Tested with OpenSSL 3.x and later.
* <a id='fn-script-is-doc'>**[3]**</a> The OpenSSL commands document the certificate parameters required for the output to be compatible with the CANsub.4.
* <a id='fn-revoke'>**[4]**</a> The curl commands include `--ssl-no-revoke` for Windows compatibility.
* <a id='fn-sha256-der'>**[5]**</a> The uploaded `.crt` is PEM (base64 text). The fingerprint is the SHA-256 of the same certificate in its DER (binary) encoding.
